# UI/UX reconfiguration: the deferred F-UIUX rollout

Date: 2026-06-17. Scope: finish the F-UIUX-* follow-ups deferred from the 2026-06-16 phase-2 bundle (0.21.0). Five SPA-only PRs (#315 to #319), all built and held for the operator merge. CHANGELOG 0.22.0.

## Why this exists

Phase 2 (0.21.0) shipped each structural surface on its flagship page and deferred the long tail to scoped F-UIUX follow-ups, so each got the right treatment rather than a risky blanket sweep. This session is that tail: roll the toasts, the interactive rail, and the hub tabs out to the remaining surfaces, and add the per-route nav capability gating. The backend trio (the default-for-org checkbox, auto-numbering, the inline draft-line UPDATE endpoint) stays held for a separate gated pass; nothing here touches the server.

## How it ran

Ultracode, auto mode. The session opened with four parallel read-only mapping agents (hub tabs, interactive rail, toasts and create flows, nav caps and eyebrow) so every unit was grounded in the real architecture before any edit. The build then went unit by unit, each on its own branch off `main` on disjoint files so the operator merges in any order. The logic-heavy units carried an adversarial review; the mechanical ones were proven by `git diff -w` plus the full gate set.

Each unit passed the same six gates locally before its PR opened: typecheck, lint at max-warnings 0, the 716-test regression suite plus the unit run (including any new tests), the contract parity test, the production build, and size-limit. The index chunk held at roughly 35.8 kB gz under the 40 kB budget across all five.

## What shipped

- **#315 toasts rollout (F-UIUX-TOASTS-ROLLOUT-01).** The quote-create next-step toast extends to ten create flows. Customer, vendor, opportunity, and contact create get an action-button toast that deep-links the next step with the new record prefilled (each target param verified before wiring); item, lead, invoice, PO, shipment, and receiving get a message-only toast. Invoice and PO use new pure, unit-tested message helpers mirroring `quoteCreatedToast`. Item and lead stay message-only on purpose: `BomCreatePage` reads no `parent_item_id` param and `OpportunityCreatePage` requires a customer a lead has no FK for, so an action button would land on a form it cannot prefill.

- **#316 interactive rail rollout (F-UIUX-RAIL-ROLLOUT-01).** The Pattern D rail extends to the opportunity, expense, purchase order, and shipment detail pages. The gate is the key: each page passes `onAdvance` only when the next happy-path step is a transition it already exposes as a manual button, checked against its own allowed-transition list and capability, and the advance maps to the same mutation the button uses. Shipment's `picking` to `shipped` step routes through the dedicated Ship action (`ship.mutate`, gated on `shipments.ship`), so the rail never offers a step the operator cannot run. A shared pure `nextStepperState` helper (added to `stateStepperPaths`, unit-tested) answers "what is the next path state". Invoice, receiving, vendor bill, and lead stay display-only (modal amount entry, dock selection, or off-page transitions do not fit a one-click advance). Adversarial review APPROVE, with a fix folded in during review to gate the shipment ship step solely on `shipments.ship`.

- **#317 project hub on tabs (F-UIUX-HUB-TABS-PROJECT-01).** The project detail page's six record sections (materials, phases, receiving, manufacturing, shipments, invoices) become tabs, matching the customer and vendor hubs. This is a pure wrapping change on a core operational page: every form, the lazy `PhasesSection` and its dnd-kit chunk split plus the Suspense fallback, the DataTable, the convert-to-invoice button and its error, and every `data-testid` are preserved verbatim. `git diff -w` shows nothing but the tab scaffolding, and the build confirmed `PhasesSection` is still a separate lazy chunk. The NextStepCTA, the FSM transition cluster, and the template snapshot stay above the tabs as the always-visible action and context zone. No `RelatedSection` conversion: those sections carry custom per-item content and test-ids, and invoices has a button rather than a link CTA, so wrapping in place was the lower-risk path. This also resolves `F-UIUX-HUB-TABS-LEAF-01` as a no-op: the sales-order and manufacturing-run detail pages were confirmed true leaf pages (a single line-item table, no sibling related-record collections).

- **#318 member hub on tabs (F-UIUX-HUB-TABS-MEMBER-01).** The KitForce member detail page is promoted from a leaf to a hub: Overview (the metadata plus the audit timeline), Assignments, Time entries, and Shifts, each filtered server-side by `member_id` through the existing list hooks. The phase-2 note flagged this as backend-blocked; it was not, the `member_id` filters already exist on all three hooks. The related lists are read-only and do not use `RelatedSection`: those entities are created via inline forms on their list pages, not via member-prefilled create routes, so a required create CTA would be misleading. Assignment and shift rows link to their detail routes; time entries render static (edit-only). The time-entry rate stays `read_rate`-gated. Shipped as its own PR so the operator can hold it independently if member should stay lean.

- **#319 per-route nav capability gating (F-UIUX-NAV-ROLE-SCOPE-PERROUTE-01).** The previously reserved `requiresCap` field is now active: each sidebar nav entry hides unless the role holds that resource's read capability, layered on the existing section gates. `visibleRoutesForMode` gains an optional `can` predicate (backward compatible, so the existing flag-only callers and tests are untouched) and the Sidebar passes the role's `useCapabilities().can`. An adversarial review verified every one of the thirty-plus caps against the canon and confirmed the minimum-visible-route invariant holds for every role and section. Routes whose resource has no read cap (every Production and Fulfillment add-on, WMS putaway) and the already-adminOnly Settings routes stay ungated, so read-only roles are never wrongly hidden from them.

## A behavioral change worth flagging

#319 is the one unit with a visible effect on existing roles. Because the per-route gate matches the capability policy precisely, non-owner roles now see fewer sidebar links than before: sales loses Vendor bills, Expenses, Stock movements, BOMs, Receiving, and the Cost dashboard; ops loses the finance ledger entries (chart of accounts, period close, journal entries) and the Cost dashboard; accounting sees only Members under Workforce. These links were previously shown to any role that passed the looser section gate even when the role could not read the resource. This is SPA render hiding only; the server stays the authority, a direct URL still renders for a permitted user, and the constitutional 403 or 404 still answers a forbidden one.

## Decisions

- **Eyebrow re-alignment (F-UIUX-EYEBROW-TASK-ALIGN-01) skipped.** PR #308 deliberately decoupled the breadcrumb eyebrow (a stable domain axis) from the sidebar (the task axis). Re-coupling would lock the eyebrow to the task structure, churn it on every future sidebar reorganization, and rewrite the R-W13-IA-01 lock, for no material UX gain. The grounding agent independently reached the same recommendation.
- **Member hub built, not held.** The follow-up was unblocked (the filters exist), it follows the proven hub pattern, and it is read-only, so it was built rather than flagged. It is its own PR so it can be rejected independently.

## Remaining deferred work

Still held for a gated backend pass, unchanged from phase 2: the tax and payment-method default-for-org checkbox, auto-numbering for credit notes and journal entries, and the inline draft-line UPDATE endpoint. Smaller, optional follow-ups spawned this session: `F-UIUX-RAIL-OPP-CLIENT-CAP-01` (the opportunity stage controls, both the existing buttons and the new rail, do not client-gate on the stage-transition cap; pre-existing, server enforces) and the manufacturing-run, production-run, and credit-note first-edge rail advances (their later edges are destructive completes or a navigate-to-apply, so they need bespoke handling).
